# 从伪共享证据到源码优化

将 DevKit 动态源码优化工具观测到的 `FS` 访问端点映射到项目源码，判断伪共享是否成立；用户明确要求“修复”“修改”或“优化”且提供源码时，实施直接相关的局部源码修改。始终区分“观测到的访问位置”“推断出的变量”和“经过验证的对象布局”。本 skill 只分析 `FS` 记录；其他记录或访问同一逻辑值的情况不在范围内，不提供诊断或修复建议。

## 使用边界

- 用户已提供 `devopt` memory 结果时直接解析，绝不再次调用 `devopt` 采集。
- 用户未提供结果时，可以使用本 skill 的采集脚本，但必须先确认目标平台具有 ARM SPE 采集能力、当前进程具有 root 权限，并已取得目标 PID 与可执行的 `devopt.sh` 路径；任一条件不满足时不执行，也不尝试安装、提权或猜测参数。
- 缺少采样、匹配符号或源码版本时，给出有边界的分析和补齐证据所需的最少材料。
- 需要理解完整分析与修改方式时读取 [端到端示例](references/example.md)。
- 默认分析并给出定位结论、证据、置信度和修改建议；用户明确要求“修复”“修改”或“优化”时，只实施伪共享直接涉及的局部源码修改。

## 数据采集

仅在没有现成 `devopt` 结果，且已确认 ARM SPE、root、PID 与 `devopt.sh` 路径四项前置条件时，运行：

```bash
bash <skill目录>/scripts/collect-memory-analysis.sh -p <PID> --devopt /XXXXX/devopt.sh
```

脚本依次执行：

```bash
/XXXXX/devopt.sh record -d <秒数> -p <PID>
/XXXXX/devopt.sh record -d <秒数> -p <PID> -m -i <本次生成的.rawdata>
/XXXXX/devopt.sh script -t memory -i <本次生成的.rawdata>
```

`--devopt` 必须指向用户解压 tar.gz 后的实际 `devopt.sh`，例如 `/XXXXX/devopt.sh`；不要假设它位于当前目录，也不要扫描整个文件系统猜测位置。`-d` 默认是 10 秒，仅在用户要求其他采集时长时显式传入。脚本默认在当前目录查找第一步新生成的单个 `*.rawdata`；文件位于其他目录时传 `--rawdata-dir DIR`。已知 rawdata 时可传 `-i FILE` 跳过第一步；需要同时落盘最终文本时传 `-o FILE`。发现零个或多个候选文件时不要猜测，按脚本提示显式指定。

不要在用户已提供报告时运行采集。采集前确认 `/sys/bus/event_source/devices/arm_spe_*` 等平台证据表明 ARM SPE 可用，并确认 `id -u` 为 `0`；不要擅自安装 `devopt`、使用 `sudo` 提权或选择其他进程。

## 分析与源码修改流程

### 1. 核对证据与版本

获取完整 memory 输出、采样进程实际运行的二进制、匹配的 debug info/符号、源码版本和原始负载信息。解释记录前完整阅读 [devopt memory 输出格式](references/devopt-memory-format.md)。

agent 当前环境与被采样应用可能不在同一机器、容器、文件系统或构建环境。只有确认比较的是同一构建产物（例如文件哈希或 build-id 一致），并正确处理 PIE/ASLR 加载基址后，才能直接比较 PC。仅凭采样记录中的 PC 与 agent 本地反汇编得到的 PC 不同，不能断言采样证据来自旧构建；差异也可能来自编译器、链接器、构建选项或布局环境。

工具不在仓库或不可执行时，以用户提供的原始输出为准；需要补采样时先查看实际 `devopt.sh --help` 或项目文档，不发明安装路径、参数、事件名或分析结果。

### 2. 解析缓存行访问

解析全部多行 `FS` 记录并按 `CacheLineAddr` 分组，保留排名、两个 PC、`Type:SS/SL`、A/B 行内偏移与宽度，以及两个符号化端点。将访问换算为半开字节区间 `[offset, offset + width)`：

- 区间不重叠：伪共享候选；
- 区间重叠、两个端点访问同一逻辑值，或记录类别不是 `FS`：不属于伪共享，排除；
- 只有缓存行地址、无法解析访问表达式或对象：证据不足。

`FS` 是本 skill 接受的记录类别，`Type:SS/SL` 是访问关系；不要混淆。PC 和源码行相同也不代表访问同一字节，必须结合 A/B 偏移、宽度和实际表达式判断。

### 3. 映射到项目源码

1. 从 A/B 的 PC、函数、模块路径和源码行定位完整内存访问表达式；一行存在多个访问时结合反汇编及 A/B 偏移区分。
2. 追踪变量声明、实际类型、分配位置、数组索引、生命周期，以及线程或 CPU 所有权。
3. 检查同一变量的所有读写端点，确认两个采样端点是否代表真实的并发关系。
4. 仅对采样进程对应的匹配二进制和符号使用 `gdb`、`addr2line`、`objdump`、DWARF 或 `pahole` 映射 PC 并检查已有布局；agent 环境中的另一个二进制只能作为源码语义参考，不能用于证明采样 PC 属于旧版本。工具不可用时降低置信度，不要求安装。
5. 考虑继承、压缩布局、自定义分配器、相邻堆对象和跨缓存行访问，避免把声明布局误当成实例布局。

只有访问表达式、线程所有权和实际对象布局相互印证时，才标记为“已确认”；否则标记为“可能”或“未解析”，并说明缺少的证据。

### 4. 诊断问题类型

- 不同线程独立更新同一缓存行内互不重叠的字段/元素：伪共享。
- 访问范围重叠，或线程访问同一逻辑值：不属于伪共享，停止分析该记录。
- 符号、版本、对象身份或布局无法对应：信息不足。
- PC、源码行或访问宽度与当前环境中的二进制不一致：先核对是否为同一构建产物及加载基址；未确认前只能标记为环境或映射差异，不能据此判定证据来自旧构建。

`SS` 表示写/写，`SL` 表示写/读；两者都不能单独证明预期所有权模型。原子操作保证某些并发语义，并不排除伪共享。

### 5. 给出或实施源码修改

用户明确要求“修复”“修改”或“优化”且提供相关源码时，阅读 [源码修改模式](references/fix-patterns.md)，选择与项目约束相符的最小方案并实施局部源码修改；否则只输出建议或补丁草案：

- 伪共享：对齐包装、拆分独立热字段、按线程/CPU 分片，或按缓存行重新划分所有权。
- 信息不足：不猜测字段或盲目添加 padding，先给出定位命令或所需材料。

源码优化只修改已确认伪共享直接涉及的源码类型、字段和访问点；不要修改 `Makefile`、CMake 文件、构建脚本、CI 配置或其他无关文件。修改时遵守项目现有类型和命名约定；检查 ABI、序列化、共享内存、FFI/JNI、持久化布局、数组密度和内存增长。不要用 `volatile`、调整内存序、加锁或仅对齐外层对象冒充布局修复。

## 输出要求

针对每个重要缓存行给出：

1. **分析证据**：原始多行记录、两个 PC/符号端点、`SS`/`SL`、缓存行、A/B 偏移、宽度和区间是否重叠。
2. **源码映射**：文件与行号、访问表达式、变量/字段/元素、声明或分配位置及置信度。
3. **诊断**：已确认伪共享、伪共享候选、信息不足或可能的映射误差，并说明线程/CPU 所有权；对排除记录只说明其不属于本 skill 范围。
4. **源码修改**：建议或实际修改的类型、字段、访问点和关键 diff。
5. **影响评估**：正确性与同步语义、ABI、内存成本和可移植性。
