# 伪共享源码修改模式

根据已经验证的对象布局和所有权关系，选择影响最小的方案。

## 分离独立热点字段

将不同线程独立写入的热点字段放入分别对齐的子对象，或将线程私有热点状态与共享冷数据拆分。

```cpp
struct alignas(64) WorkerCounter {
    std::atomic<std::uint64_t> value;
};
struct State {
    WorkerCounter producer;
    WorkerCounter consumer;
};
```

不要假定所有平台的缓存行都是 64 字节。优先使用可靠的平台常量，并验证 `sizeof`、`alignof` 和 `offsetof`，尤其注意数组元素步长。

## 按线程或 CPU 分片

将频繁写入的全局计数器改为私有分片，并在非热点路径汇总。每个分片必须独占缓存行；多个小型原子变量组成的数组仍会伪共享。说明读取语义、汇总时机和内存成本。

## 密集数组或相邻对象

使用对齐包装类型、按缓存行分块所有权或划分连续区间。检查分配器的起始地址对齐和元素步长，扩大大型数组元素前先量化内存增长。

## 热冷数据拆分

将只读或低频元数据从频繁修改的线程私有状态中移出，兼顾降低竞争和缓存占用。

## 避免无效修改

- 修改内存序不能将数据移到不同缓存行。
- `volatile` 既不提供线程同步，也不能解决共享问题。
- 互斥锁可能恢复正确性，但不是布局修复，并可能加重竞争。
- 盲目填充可能转移竞争、破坏 ABI 或浪费内存。
- 未验证最终偏移就调整字段顺序只是猜测。
## 方案选择表

| 已验证现象 | 优先方案 | 需要验证 |
| --- | --- | --- |
| 同一对象内两个独立热字段 | 对齐包装或拆分热状态 | 字段偏移、包装大小、对象起始对齐 |
| 数组相邻元素由不同线程写 | 对齐元素包装或按缓存行分块所有权 | 数组元素步长、总内存增长 |
| 按 CPU 分片 | 每 CPU 独占缓存行 | 线程迁移、CPU 热插拔、索引边界 |
| 相邻堆对象互相干扰 | 对齐分配器或尺寸分级 | 分配起始地址、释放和复用路径 |

## 对齐实现检查

- 给外层对象添加 `alignas(N)` 只保证对象起点，不保证内部两个热字段被分隔。
- 对数组使用包装元素类型，并同时检查 `alignof(Element) >= N` 与 `sizeof(Element) % N == 0`。
- 自定义 allocator、placement new 和共享内存映射必须兑现请求的 over-alignment；只验证类型声明不够。
- 按 CPU 分片时，若线程可能迁移，不能在一次更新中分别读取两次 CPU id；应获取稳定索引，或使用项目已有的 per-CPU 设施。

## 修改后必须保持的语义

- 原子计数器的内存序不因布局修复而擅自改变。
- 局部累计与批量归约必须定义何时对读者可见，以及线程结束时如何 flush。
